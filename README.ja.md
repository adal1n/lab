## 1. アカウントハイジャック — 技術的全貌

### 1.1 中心となる関数

`SystemPacketSend::RequestLogin(int type, std::string const& s1, std::string const& s2)` がログイン要求を生成する唯一の関数です。`type` の値によって2種類のログインパケットのいずれかを構築します。

- **`type == 2`（プラットフォームログイン、Google Play Games/Game Centerと推定）:** プラットフォームのプレイヤーID、ニックネーム、国コードなどを含めて送信。
- **`type != 2`（番号/UIDログイン）:** 以下のフィールドのみを送信し、`s1` は一切読み込まない。

### 1.2 実際に送信される値 — アカウントUIDのみ

`type != 2` の経路がサーバーへ送る内容を最後まで追跡した結果:

```
type = （ハンドシェイクの中で決まる値）
s1   = ""  （未使用 — コードがそもそも読み込まない）
s2   = ""  （自動トリガー経路では最後まで空文字列のまま — 確認済み）
```

**実際に意味を持つ値は `GetMyClientData()+0x2124` の4バイト整数ただ一つです。** このフィールドはサーバー発行のセッショントークンでも、クッキーでも、タイムスタンプでもありません — 純粋な数値です。

### 1.3 このフィールドが「アカウントUID」であるという根拠（独立した2つの証拠）

1. **ギルドメンバー名簿の照会:** `UIClanMain_Renewal::UpdateMyInfoLayout()` がこのフィールドを、`GuildMgr` のギルドメンバー名簿（`std::_Rb_tree<unsigned int, pair<unsigned int const, GuildMemberRecord*>>`）から「自分の項目」を検索するキーとして使用。このマップは明示的に `unsigned int` をキーとして宣言しており、`GuildMgr::findGuildMemberRecord(GuildRecord*, unsigned int)` という上位関数のシグネチャもこれを裏付けている。
2. **バトルロイヤル・デュオマッチング（ギルドシステムとは無関係の別機能）:** `SystemPacketSend::JoinBattleRoyalDuo()` が同じフィールドを `unsigned int` として読み込み、マッチングサーバーへそのまま送信。マッチングを成立させるにはサーバーが「これが誰からの要求か」を知る必要があるため、この値も論理的に「自分のアカウント固有ID」でしかあり得ない。

互いに無関係な2つの機能が独立して同じ結論に達しているという点で、**静的解析だけで得られる最大限の確信度**と言えます。

### 1.4 この要求が自動的に発生する条件

`LobbyScene::OnReceive`（サーバーパケット受信ハンドラ）内で、サーバーの特定のハンドシェイク応答の直後、以下の3条件がすべて満たされるとクライアントが自動的にこのログイン要求を送信します。

1. ローカルストレージ（`UserDefault`）の特定のキーに保存された値が存在せず、
2. プラットフォームSDKのプレイヤーIDは存在し、
3. 特定のJNI（Javaブリッジ）呼び出しが失敗した場合。

つまりこれは「ユーザーが番号を入力してログインボタンを押す」フローではなく、**再接続時に自動的に発生する、サイレントなバックグラウンドハンドシェイク**です。

### 1.5 暗号化が防御にならない理由

パケットはAESで暗号化されていますが、`TCPSocketManager::setCodeKey` を追跡した結果、**鍵/IV自体が接続ごとにサーバーが平文のハンドシェイクで渡してくる値**であることが分かりました。すでにプロトコルをリバースエンジニアリング済みの攻撃者にとっては実質的な防壁になりません。

### 1.6 なぜ「管理者アカウント1番」のシナリオより「全ユーザー大規模乗っ取り」の方が正確な見立てなのか

クライアント全体を調査しましたが、GM/管理者/運営者権限という概念自体が存在しません（「Grade」という名前が付くものはすべてリーグ/ランキング等級のみ）。正常に設計されたサービスであれば、実際の管理ツールは一般プレイヤーのログインとは完全に分離された別の認証体系で運用するのが標準であるため、低いUIDを奪取しても「管理者パネルの掌握」より「初期に登録した一般アカウントの乗っ取り」である可能性が高いです。

**本当の最悪のシナリオは別にあります:** もしサーバー側のアカウントUIDが連番整数（よくあるauto-increment方式）であれば、攻撃者は特定の被害者を狙う必要すらなく、**UIDを0から順に総当たりで送信するだけで全ユーザーのアカウントを自動的・大規模に乗っ取れます。** これは「管理者アカウント1つ」よりもはるかに大規模な事故です。

## 2. セッションハイジャック — アカウントハイジャックとは異なる2つの図式

「セッションハイジャック」という言葉が指しうる、まったく異なる2つの攻撃を区別する必要があります。

### 2.1 図式A —「新しいセッションを被害者になりすまして開く」（＝実質的に第1章の結果、可能）

攻撃者がUIDの偽装により被害者アカウントの**新しい**ログインセッションを開けた場合、その瞬間からサーバーにとってその接続は「被害者本人」になります。この状態からは、そのアカウント権限内のあらゆる行為が可能になります。

- **チートオペコードの悪用:** `CheatSetGold`、`CheatSetMoney` など20種類以上の関数が権限検証用のフィールドをパケットに一切含んでいません — サーバーがホワイトリスト検証なしに実行してしまうなら、そのまま悪用可能です。
- **`ReportUser` による任意アカウントの強制BAN:** 通報対象が生のuint一つだけで、「実際にそのユーザーと遭遇した」という証拠がパケットにありません。サーバーが通報履歴だけで自動制裁を行うなら、番号さえ分かれば任意のユーザーをBANできます。
- **ギルド加入承認・ギルドマスター委譲の強奪:** `ClanAcceptWaitingUserToJoin`、`ClanChangeMemberGrade` はいずれも対象IDのみを含み、「誰が送信したか」はパケットにありません — 被害者がギルドマスターであれば、その権限で攻撃者のアカウントを加入・昇格させられます。

**これらはすべて新たな脆弱性ではなく、第1章のログイン脆弱性の直接的な派生結果です。** ログインの一点を塞げば、これらのシナリオはすべて同時に遮断されます。

### 2.2 図式B —「すでに接続中の生きているセッションへこっそり割り込む」（根拠なし）

これはまったく異なる、はるかに難しい攻撃です — 進行中のTCP接続をリアルタイムで乗っ取るネットワークレベルのハイジャック（シーケンス番号の予測、同一ネットワーク経由、ARPスプーフィングなど）が必要になります。**今回の分析ではこれが可能だという根拠は一切発見できませんでした。** 確認するにはまったく異なる種類の（ネットワークプロトコルレベルの）調査が必要であり、これはクライアントバイナリのリバースエンジニアリングの範囲を超えています。

### 2.3 新たな発見 — クライアントに重複ログイン防止UIが存在しない

「別の端末で接続中」「重複ログイン」に関するメッセージ/処理ロジックをクライアント全体で探しましたが、**まったく見つかりませんでした。** これがサーバー側にそもそもそういうポリシーがないという意味なのか、それともサーバーから送られてくる汎用テキストメッセージとしてのみ処理されているためクライアントコードに固定文字列として残っていないだけなのかは、クライアント解析だけでは区別できません。**ただし、もし前者であれば、攻撃者が偽装ログインで入っても本物の所有者の既存セッションが強制終了されず、2つのセッションが同時に存在しうることになります。この場合、被害者は自分のアカウントが乗っ取られたことに気づく方法すらないかもしれません。** この点はサーバーチームによる確認が必須です。

## 3. インフラに関する発見

バイナリの文字列検索から、実際の運用に関する情報も確認されました。

- `gameparadiso.iptime.org` — **韓国のルーターメーカー（ipTIME）が提供する家庭用/SOHO向け無料DDNSサービス** のドメイン。ユーザー自身の確認により `222.112.0.210` に解決されることが判明しています。商用ゲームのインフラがこのような名前を使うのは異例で、社内のテスト/開発サーバーがルーターの背後で外部に露出しているパターンに見えます。
- `http://pl.gameparadiso.com:15667/gameparadiso_return` — 決済（PG）コールバックと推定されるURLですが、**平文のHTTP** です。
- ログインサーバー（`47.74.37.170:16000`）とは別のホストと見られます。

このIPに対する実際の接続・ポートスキャンなどのネットワーク調査は実施していません — 社内で直接確認する必要があります。

## 4. DB/サーバーへの直接アクセス用クレデンシャル — なし

`libMyGame.so` の全文字列とシンボルを対象に、DB接続文字列、平文クレデンシャル、生のSQL、クラウドキー、バックドア/隠し機能に関するキーワード、Luaバックドアを全数検索しましたが、**すべてヒット0件** でした。ゲームクライアントはそもそもDBに直接接続する構造ではないため、これは正常な結果です。（ただし、他の `.so` やAPKのJava/Kotlin領域、サーバー自体は今回の検索範囲外です。）

## 5. 確定に必要なサーバー側の確認事項（優先順位順）

1. **【最優先】** `type != 2` ログインがUIDのみで（あるいは形式チェック程度の `s2` だけで）承認されるのか、それともサーバーが別途署名付きセッショントークンを要求するのか。
2. **【最優先】** アカウントUIDの採番が連番整数なのか、予測不可能な値なのか — 結果によって事故の規模が「特定の被害者」から「全ユーザー」まで変わります。
3. アカウントごとの同時セッション制限ポリシーが実際に存在するか（2.3参照）。
4. `type == 2` プラットフォームログイン時、プレイヤーIDをGoogle/Appleへサーバー間で再検証しているか。
5. `ReportUser` の処理時に、通報者と対象者の間に実際の相互作用（同じマッチ/パーティ）があったかを照合しているか。
6. チートオペコード受信時にホワイトリストのアカウントのみ実行するのか、それとも実行後の事後BANなのか。
7. サーバーログにおいて、`type != 2` ログイン要求のUIDが短時間に連続して記録された履歴があるか（自動化された攻撃の痕跡確認）。

## 6. 推奨対応（優先順位順）

1. `type != 2` ログイン経路にサーバー発行の署名付きセッショントークン/OTP検証を必須化 — 識別子（UID）単独での承認は即時禁止。
2. アカウントUIDを予測不可能な値（UUIDなど）に変更するか、少なくともUIDの連番スキャンをレート制限・異常検知でブロック。
3. アカウントあたりセッション1つに制限し、新規ログイン時に既存セッションを終了させ、所有者に通知。
4. AES鍵交換を平文ハンドシェイクではなくTLSに置き換える。
5. `ReportUser` の自動制裁に実際の相互作用検証を追加。
6. チートオペコードのホワイトリスト事前検証（実行前にブロック、事後BANではなく）。
7. `gameparadiso.iptime.org` インフラの実使用状況を確認した上で正式なIDC/クラウドへ移行または廃止し、決済コールバックをHTTPSへ転換。
8. ログイン成功/失敗＋IP/端末情報のログ記録および異常パターンの監視。

## 7. 提供された検証ツール

`poc_requestlogin_frida.js`（分析ブランチ）を使って、自分が所有するテストアカウント2つで上記の仮説を直接検証できます。

- **ステップ1（観察）:** 実行中のクライアントにフックして、実際のUIDとトリガー条件を実測。
- **ステップ2（注入、テストアカウント限定）:** `Common::GetMyClientData()` をフックして `+0x2124`（実際の注入ポイント）をテストアカウントBのUIDにその場で書き換え、サーバーが実際にログインさせるかを確認。

**実際の他プレイヤーのUIDを対象に絶対に使用しないでください。**
