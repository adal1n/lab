# mc4 — 타인 유저ID 무단 로그인 취약점 분석 / 他人のユーザーIDによる不正ログイン脆弱性分析

> 정적 바이너리 분석(리버싱) 기반 보고서. 라이브 서버에 대한 실제 침투 테스트는 수행하지 않았습니다.
> 静的バイナリ解析（リバースエンジニアリング）に基づく報告書です。本番サーバーへの実際の侵入テストは実施していません。

## 한국어

### 1. 결론 요약

`libMyGame.so`(안드로이드 클라이언트, ARM64)를 디스어셈블한 결과, **로그인 패킷 하나가 서버 발급 세션 토큰 없이, 클라이언트가 스스로 채워 넣는 "계정 숫자 ID(UID)"만으로 로그인을 요청하는 구조**임을 확인했습니다. 이 UID가 서버에서 예측 가능한 방식(순차 발급 등)으로 채번된다면, **특정 피해자를 지목할 필요 없이 UID를 순회하는 것만으로 전체 이용자 계정을 자동·대량으로 탈취할 수 있는 구조**입니다. 다만 마지막 확정 단계(서버가 실제로 이렇게 처리하는지)는 서버 코드 확인이 필요합니다.

### 2. 기술적 근거

- 대상 함수: `SystemPacketSend::RequestLogin(int type, std::string const& s1, std::string const& s2)`
- 이 함수는 `type` 값에 따라 두 가지 로그인 패킷을 만듭니다.
  - **`type == 2` (플랫폼 로그인, Google Play Games/Game Center 추정):** 플랫폼 플레이어 ID(`GetSafeSdkboxPlayerID()`), 닉네임, 국가코드 등을 함께 전송.
  - **`type != 2` (번호/UID 로그인):** 아래 두 값만 전송하고 나머지는 아예 읽지도 않습니다.
    1. **`GetMyClientData()+0x2124`** — 4바이트 정수. `.text` 전체(약 45MB, 1,130만 줄 디스어셈블) 교차 검증 결과, 이 오프셋은 `UIClanMain_Renewal::UpdateMyInfoLayout()`에서 **길드원 명단을 계정 UID로 조회하는 검색 키**로 재사용되는 걸 확인했습니다. → **이 필드 = 해당 계정의 전역 숫자 UID(계정 고유번호)**.
    2. **`s2`** — 짧은 문자열(최대 255바이트). `Common::SetPhone(char*, unsigned int)`을 보면 "번호"라는 게 실제로는 `sprintf(buf, "%u", 순수정수)`로 만든 뒤 하이픈을 끼워 전화번호처럼 보이게 포맷한 것일 뿐, SMS 인증을 거친 진짜 통신사 전화번호라는 증거는 없습니다. 즉 이 "번호" 체계도 결국 정수 ID 공간과 맞닿아 있을 가능성이 높습니다.
- 이 로그인 요청(`type != 2`)을 트리거하는 네이티브 코드 경로는 `LobbyScene::OnReceive`(서버 패킷 수신 핸들러) 안에 단 한 곳뿐이며, 서버가 보낸 핸드셰이크 패킷 내용을 그대로 되돌려 보내는 구조입니다. AES 암호화는 걸려 있으나 **키/IV 자체도 연결마다 서버가 평문 핸드셰이크로 내려주는 값**이라(정확한 파생 알고리즘은 별도 확인 필요), 이미 프로토콜을 분석한 공격자에게는 실질적 장벽이 되지 못합니다.

### 3. 공격 경로 (성립 가능성 순서대로)

1. 리버싱으로 패킷 포맷(위 구조), AES 키 전달 방식, 오피코드를 확보한다 — **이번 분석으로 이미 대부분 확보됨.**
2. `type != 2` 로그인 패킷의 UID 필드를 임의 값으로 채워 전송한다 (Frida로 실행 중인 클라이언트를 후킹하거나, 프로토콜을 직접 구현한 별도 툴 사용).
3. 서버가 **UID만으로(또는 `s2`를 형식 체크 수준으로만 확인하고) 로그인을 승인**한다면 → 그 UID 계정으로 완전히 로그인됨. 이후 치트 오피코드 사용, `ReportUser`를 이용한 임의 계정 강제 밴, 클랜 가입수락·마스터 위임 등 해당 계정 권한 내 모든 행위가 가능해짐 (전부 별도 분석에서 확인).
4. 만약 서버 UID가 순차 정수라면, 2~3번을 0부터 반복 = **전체 계정 자동 순회 탈취.**

### 4. 확정되지 않은 것 (서버 확인 필요, 우선순위 최상위)

| 항목 | 결과에 따른 영향 |
|---|---|
| 서버 UID 채번이 순차적인가, 추측 불가능한가 | 순차적이면 "특정 피해자 공격" → "전체 이용자 대상 대량 탈취"로 심각도 격상 |
| `s2`가 서버가 그 계정에만 발급한 진짜 검증 토큰인가, 형식만 맞으면 통과되는 값인가 | 후자면 UID만으로 로그인 성립 = 확정적 취약. 전자면 UID를 알아도 로그인 불가 |
| 서버 로그에 `type != 2` 로그인 요청의 UID가 짧은 시간 내 연속으로 찍힌 이력이 있는가 | 있다면 이미 자동화된 스캐닝/공격이 진행됐다는 증거 |

### 5. 권고 조치 (우선순위순)

1. **최우선:** `type != 2` 로그인 경로에 서버가 발급한 서명된 세션 토큰/OTP 검증 필수화. 식별자(UID/번호) 단독 승인 즉시 차단.
2. 계정 UID를 예측 불가능한 값(UUID 등)으로 전환하거나, 최소한 UID 순차 스캐닝을 rate limit/이상탐지로 차단.
3. 계정당 세션 1개 제한, 신규 로그인 시 기존 세션 종료 + 알림.
4. AES 키 교환을 평문 핸드셰이크가 아닌 TLS로 대체.
5. 짧은 시간 내 다수 계정 로그인 시도 → rate limiting, 로그인 성공/실패 + IP/기기 로그 적재.

## 日本語

### 1. 結論の要約

`libMyGame.so`（Androidクライアント、ARM64）を逆アセンブルした結果、**ログインパケットの一つが、サーバー発行のセッショントークンなしに、クライアント自身がローカルで保持している「アカウントの数値ID（UID）」だけでログインを要求する構造**であることを確認しました。このUIDがサーバー側で予測可能な方式（連番発行など）で割り当てられている場合、**特定の被害者を狙う必要すらなく、UIDを総当たりするだけで全ユーザーのアカウントを自動的・大規模に乗っ取れる構造**になります。ただし最終確定（サーバーが実際にそう処理しているか）にはサーバー側コードの確認が必要です。

### 2. 技術的根拠

- 対象関数: `SystemPacketSend::RequestLogin(int type, std::string const& s1, std::string const& s2)`
- この関数は `type` の値によって2種類のログインパケットを構築します。
  - **`type == 2`（プラットフォームログイン、Google Play Games/Game Centerと推定）:** プラットフォームのプレイヤーID（`GetSafeSdkboxPlayerID()`）、ニックネーム、国コードなどを送信。
  - **`type != 2`（番号/UIDログイン）:** 以下の2つの値だけを送信し、それ以外（`s1`）は一切読み込みません。
    1. **`GetMyClientData()+0x2124`** — 4バイトの整数。`.text`セクション全体（約45MB、1,130万行の逆アセンブル結果)を突き合わせた結果、このオフセットは `UIClanMain_Renewal::UpdateMyInfoLayout()` にて **ギルドメンバー名簿をアカウントUIDで検索するためのキー**として再利用されていることを確認しました。→ **このフィールド＝当該アカウントのグローバルな数値UID（アカウント固有番号）**。
    2. **`s2`** — 短い文字列（最大255バイト）。`Common::SetPhone(char*, unsigned int)` を見ると、「番号」は実際には `sprintf(buf, "%u", 純粋な整数)` で生成した後、ハイフンを挿入して電話番号のように見せているだけで、SMS認証を経た本物の通信キャリアの電話番号である証拠はありません。つまりこの「番号」体系も、結局は整数ID空間と直結している可能性が高いです。
- この `type != 2` ログイン要求をトリガーするネイティブコード経路は `LobbyScene::OnReceive`（サーバーパケット受信ハンドラ）内のただ一箇所のみで、サーバーが送ってきたハンドシェイクパケットの内容をそのまま送り返す構造になっています。AES暗号化は行われていますが、**鍵/IV自体も接続ごとにサーバーが平文のハンドシェイクで渡してくる値**であり（正確な導出アルゴリズムは別途要確認）、すでにプロトコルを解析済みの攻撃者にとっては実質的な防壁になりません。

### 3. 攻撃経路（成立可能性の高い順）

1. リバースエンジニアリングによりパケット形式（上記構造）、AES鍵の受け渡し方式、オペコードを把握する — **今回の分析でほぼ確保済み。**
2. `type != 2` ログインパケットのUIDフィールドを任意の値に書き換えて送信する（Fridaで実行中のクライアントをフックする、またはプロトコルを独自実装した別ツールを使用する）。
3. サーバーが **UIDだけで（あるいは `s2` を形式チェック程度にしか見ずに）ログインを許可**した場合 → そのUIDのアカウントに完全にログインされてしまいます。以降、チートオペコードの使用、`ReportUser` を悪用した任意アカウントの強制BAN、ギルド加入承認・ギルドマスター委譲など、そのアカウント権限内のあらゆる行為が可能になります（いずれも別途分析で確認済み）。
4. もしサーバーのUIDが連番整数であれば、2〜3を0から繰り返すことで＝**全アカウントの自動的な総当たり乗っ取り**が可能になります。

### 4. まだ確定していない事項（サーバー側の確認が最優先）

| 項目 | 結果による影響 |
|---|---|
| サーバー側のUID採番が連番か、予測不可能な値か | 連番なら「特定被害者への攻撃」→「全ユーザー対象の大規模乗っ取り」へと深刻度が格上げ |
| `s2` がサーバーがそのアカウント専用に発行した本物の検証トークンか、形式さえ合えば通るだけの値か | 後者ならUIDだけでログイン成立＝確定的な脆弱性。前者ならUIDを知っていてもログイン不可 |
| サーバーログに `type != 2` ログイン要求のUIDが短時間に連続して記録された履歴があるか | あればすでに自動化されたスキャン・攻撃が行われた証拠 |

### 5. 推奨対応（優先順位順）

1. **最優先:** `type != 2` ログイン経路に、サーバー発行の署名付きセッショントークン/OTP検証を必須化。識別子（UID/番号）単独での承認は即時に禁止する。
2. アカウントUIDを予測不可能な値（UUIDなど）に変更するか、少なくともUIDの連番スキャンをレート制限・異常検知でブロックする。
3. アカウントあたりセッション1つに制限し、新規ログイン時に既存セッションを終了＋通知。
4. AES鍵交換を平文ハンドシェイクではなくTLSに置き換える。
5. 短時間に多数アカウントへのログイン試行 → レート制限、ログイン成功/失敗＋IP/端末情報のログ記録。
