## 1. 계정 하이재킹 — 기술적 전모

### 1.1 핵심 함수

`SystemPacketSend::RequestLogin(int type, std::string const& s1, std::string const& s2)`가 로그인 요청을 만드는 유일한 함수입니다. `type` 값에 따라 두 가지 로그인 패킷 중 하나를 만듭니다.

- **`type == 2` (플랫폼 로그인, Google Play Games/Game Center 추정):** 플랫폼 플레이어 ID, 닉네임, 국가코드 등을 담아 전송.
- **`type != 2` (번호/UID 로그인):** 아래 필드만 전송하고 `s1`은 아예 읽지도 않음.

### 1.2 실제로 전송되는 값 — 계정 UID 하나뿐

`type != 2` 경로가 서버로 보내는 값을 끝까지 추적한 결과:

```
type = (핸드셰이크에서 결정되는 값)
s1   = ""  (사용 안 됨 — 코드가 아예 안 읽음)
s2   = ""  (자동 트리거 경로에서는 끝까지 빈 문자열로 유지됨 — 확인됨)
```

**실제로 실리는 유의미한 값은 `GetMyClientData()+0x2124` 4바이트 정수 하나뿐입니다.** 이 필드는 서버 발급 세션 토큰도, 쿠키도, 타임스탬프도 아닙니다 — 순수한 숫자입니다.

### 1.3 이 필드가 "계정 UID"라는 근거 (독립적인 두 가지 증거)

1. **길드원 명단 조회:** `UIClanMain_Renewal::UpdateMyInfoLayout()`이 이 필드를 `GuildMgr`의 길드원 명단(`std::_Rb_tree<unsigned int, pair<unsigned int const, GuildMemberRecord*>>`)에서 "내 항목"을 찾는 검색 키로 사용. 이 맵은 명시적으로 `unsigned int`를 키로 선언하며, `GuildMgr::findGuildMemberRecord(GuildRecord*, unsigned int)`라는 상위 함수 시그니처도 이를 뒷받침.
2. **배틀로얄 듀오 매칭 (길드 시스템과 무관한 별개 기능):** `SystemPacketSend::JoinBattleRoyalDuo()`가 같은 필드를 `unsigned int`로 읽어 매칭 서버에 그대로 전송. 매칭 성립을 위해 서버가 "이게 누구 요청인지" 알아야 하므로, 이 값도 논리상 "내 계정 고유 ID"일 수밖에 없음.

서로 무관한 두 기능이 독립적으로 같은 결론에 도달한다는 점에서, **정적 분석만으로 얻을 수 있는 최대 확신 수준**입니다.

### 1.4 이 요청이 자동 발생하는 조건

`LobbyScene::OnReceive`(서버 패킷 수신 핸들러)에서 서버의 특정 핸드셰이크 응답 직후, 다음 3개 조건이 모두 맞으면 클라이언트가 자동으로 이 로그인 요청을 보냅니다:

1. 로컬 저장소(`UserDefault`)의 특정 키에 저장된 값이 없고,
2. 플랫폼 SDK 플레이어 ID는 존재하며,
3. 특정 JNI(Java 브릿지) 조회가 실패한 경우.

즉 이건 "사용자가 번호를 입력해서 로그인 버튼을 누르는" 흐름이 아니라, **재접속 시 자동으로 발생하는 조용한 백그라운드 핸드셰이크**입니다.

### 1.5 암호화가 방어가 안 되는 이유

패킷은 AES로 암호화되지만, `TCPSocketManager::setCodeKey`를 추적한 결과 **키/IV 자체가 연결마다 서버가 평문 핸드셰이크로 내려주는 값**입니다. 이미 프로토콜을 리버싱한 공격자에게는 실질적 장벽이 되지 못합니다.

### 1.6 왜 "관리자 계정 1번" 시나리오보다 "전체 이용자 대량 탈취"가 더 정확한 그림인가

클라이언트 전체를 뒤져봤지만 GM/관리자/운영자 권한 개념 자체가 존재하지 않습니다("Grade"라는 이름이 붙은 건 전부 리그/랭킹 등급뿐). 정상적으로 설계된 서비스라면 실제 관리 도구는 일반 플레이어 로그인과 완전히 분리된 별도 인증 체계로 운영하는 게 표준이므로, 낮은 UID를 탈취해도 "관리자 패널 장악"보다는 "이른 시기에 가입한 평범한 계정 탈취"일 가능성이 높습니다.

**진짜 최악의 시나리오는 다릅니다:** 만약 서버의 계정 UID가 순차 정수(흔한 auto-increment 방식)라면, 공격자는 특정 피해자를 지목할 필요 없이 **UID를 0부터 순서대로 반복 전송하는 것만으로 전체 이용자 계정을 자동·대량으로 순회 탈취**할 수 있습니다. 이건 "관리자 계정 하나"보다 훨씬 큰 규모의 사고입니다.

## 2. 세션 하이재킹 — 계정 하이재킹과는 다른 두 가지 그림

"세션 하이재킹"이라는 말이 가리킬 수 있는 두 가지 완전히 다른 공격을 구분해야 합니다.

### 2.1 그림 A — "새 세션을 피해자 행세로 여는 것" (= 사실상 위 1장의 결과, 가능)

공격자가 UID 위조로 피해자 계정의 **새로운** 로그인 세션을 열 수 있다면, 그 순간부터 서버 입장에서 그 연결은 "피해자 자신"입니다. 이 상태에서 그 계정 권한 내 모든 행위가 가능해집니다:

- **치트 오피코드 악용:** `CheatSetGold`, `CheatSetMoney` 등 20여 개 함수가 권한 검증 필드를 패킷에 전혀 담지 않음 — 서버가 화이트리스트 검증 없이 실행부터 한다면 그대로 악용 가능.
- **`ReportUser`로 임의 계정 강제 밴:** 신고 대상이 raw uint 하나뿐이고 "실제로 그 유저와 마주쳤다"는 증거가 패킷에 없음. 서버가 신고 이력만으로 자동 제재한다면 번호만 알아도 임의 유저를 밴시킬 수 있음.
- **클랜 가입수락·마스터 위임 강탈:** `ClanAcceptWaitingUserToJoin`, `ClanChangeMemberGrade` 모두 대상 ID만 담을 뿐 "누가 보냈는지"는 패킷에 없음 — 피해자가 클랜마스터라면 그 권한으로 공격자 계정을 가입·승격시킬 수 있음.

**이건 전부 새로운 취약점이 아니라 1장 로그인 취약점의 직접적인 파생 결과**입니다. 로그인 지점 하나를 막으면 이 시나리오 전부가 동시에 차단됩니다.

### 2.2 그림 B — "이미 접속 중인 살아있는 세션에 몰래 끼어드는 것" (근거 없음)

이건 완전히 다른, 훨씬 어려운 공격입니다 — 진행 중인 TCP 연결을 실시간으로 가로채는 네트워크 레벨 하이재킹(시퀀스 번호 예측, 동일 네트워크 경유, ARP 스푸핑 등)이 필요합니다. **이번 분석에서 이게 가능하다는 근거는 전혀 발견하지 못했습니다.** 확인하려면 완전히 다른 종류의(네트워크 프로토콜 레벨) 조사가 필요하며, 이건 클라이언트 바이너리 리버싱의 범위를 벗어납니다.

### 2.3 추가 발견 — 중복 로그인 방지 UI가 클라이언트에 없음

"이미 다른 기기에서 접속 중"이나 "중복 로그인" 관련 메시지/처리 로직을 클라이언트 전체에서 찾아봤지만 **전혀 발견되지 않았습니다.** 이게 서버가 아예 그런 정책이 없다는 뜻인지, 아니면 서버가 보낸 일반 텍스트 메시지로만 처리돼서 클라이언트 코드에 고정 문자열로 남지 않은 것뿐인지는 클라이언트 분석만으로 구분할 수 없습니다. **다만 만약 전자라면, 공격자가 위조 로그인으로 들어가도 진짜 소유자의 기존 세션이 강제 종료되지 않아 두 세션이 동시에 존재할 수 있고, 이 경우 피해자는 계정이 도용됐다는 걸 알아챌 방법조차 없을 수 있습니다.** 이 부분은 서버팀 확인이 꼭 필요합니다.

## 3. 인프라 관련 발견

바이너리 문자열 검색에서 실제 운영 관련 정보도 확인됐습니다:

- `gameparadiso.iptime.org` — **한국 공유기 업체(ipTIME)의 가정용/소호 DDNS 서비스** 도메인. 사용자가 직접 확인한 결과 `222.112.0.210`으로 resolve됩니다. 상용 게임 인프라가 이런 이름을 쓰는 건 이례적이며, 사내 테스트/개발 서버가 공유기 뒤에서 외부 노출된 패턴으로 보입니다.
- `http://pl.gameparadiso.com:15667/gameparadiso_return` — 결제(PG) 콜백으로 추정되는 URL인데 **평문 HTTP**입니다.
- 로그인 서버(`47.74.37.170:16000`)와는 별개의 호스트로 보입니다.

이 IP에 대한 실제 접속/포트스캔 등 네트워크 조회는 수행하지 않았습니다 — 사내에서 직접 확인이 필요합니다.

## 4. DB/서버 직접 접근 크리덴셜 — 없음

`libMyGame.so`의 전체 문자열과 심볼을 대상으로 DB 연결 문자열, 평문 크리덴셜, 원본 SQL, 클라우드 키, 백도어/은닉 기능 키워드, Lua 백도어를 전수 검색했으나 **전부 히트 0건**이었습니다. 게임 클라이언트는 원래 DB에 직접 붙는 구조가 아니므로 정상적인 결과입니다. (단, 다른 `.so`나 APK의 Java/Kotlin 영역, 서버 자체는 이번 검색 범위 밖입니다.)

## 5. 확정에 필요한 서버 확인 사항 (우선순위순)

1. **[최우선]** `type != 2` 로그인이 UID만으로(또는 형식 체크 수준의 `s2`만으로) 승인되는지, 아니면 서버가 별도의 서명된 세션 토큰을 요구하는지.
2. **[최우선]** 계정 UID 채번이 순차 정수인지, 추측 불가능한 값인지 — 결과에 따라 사고 규모가 "특정 피해자" ↔ "전체 이용자"로 갈립니다.
3. 계정당 동시 세션 제한 정책이 실제로 있는지 (2.3 참고).
4. `type == 2` 플랫폼 로그인 시 플레이어 ID를 Google/Apple에 서버-투-서버로 재검증하는지.
5. `ReportUser` 처리 시 신고자-대상자 간 실제 상호작용(같은 매치/파티) 여부를 대조하는지.
6. 치트 오피코드 수신 시 화이트리스트 계정만 실행하는지, 아니면 실행 후 사후 밴인지.
7. 서버 로그에서 `type != 2` 로그인 요청의 UID가 짧은 시간 내 연속으로 찍힌 이력이 있는지 (자동화 공격 정황 확인).

## 6. 권고 조치 (우선순위순)

1. `type != 2` 로그인 경로에 서버 발급 서명 세션 토큰/OTP 검증 필수화 — 식별자(UID) 단독 승인 즉시 차단.
2. 계정 UID를 추측 불가능한 값(UUID 등)으로 전환하거나, 최소한 UID 순차 스캐닝을 rate limit/이상탐지로 차단.
3. 계정당 세션 1개 제한 + 신규 로그인 시 기존 세션 종료 및 소유자에게 알림.
4. AES 키 교환을 평문 핸드셰이크 대신 TLS로 대체.
5. `ReportUser` 자동 제재에 실제 상호작용 검증 추가.
6. 치트 오피코드 화이트리스트 사전 검증(실행 전 차단, 사후 밴 아님).
7. `gameparadiso.iptime.org` 인프라 실사용 여부 확인 후 정식 IDC/클라우드로 이전 또는 폐기, 결제 콜백 HTTPS 전환.
8. 로그인 성공/실패 + IP/기기정보 로그 적재 및 이상패턴 모니터링.

## 7. 제공된 검증 도구

`poc_requestlogin_frida.js`(분석 브랜치)를 통해 본인 소유 테스트 계정 2개로 위 가설을 직접 검증할 수 있습니다:

- **1단계(관찰):** 실행 중인 클라이언트에 후킹해서 실제 UID/트리거 조건을 실측.
- **2단계(주입, 테스트 계정 한정):** `Common::GetMyClientData()`를 후킹해 `+0x2124`(실제 주입 지점)를 테스트 계정 B의 UID로 즉석 치환, 서버가 실제로 로그인시켜주는지 확인.

**절대 임의의 실제 플레이어 UID를 대상으로 사용하지 마십시오.**
